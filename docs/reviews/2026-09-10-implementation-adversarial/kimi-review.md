# Adversarial review: OpenMS 4 package experiment

## 1. Overall assessment

The extraction is structurally honest: the core/CLI/product direction of dependencies is real (I verified core has no `OpenMS/APPLICATIONS` includes other than `ConsoleUtils.h`, that OpenSwathAlgo tests link without libOpenMS, that GUI public headers do not include CLI headers, and that no consumer uses `add_subdirectory` on core). The artifact verifier, the invalid-data-override subprocess assertion, and the lock/pin tests are well designed and include genuine negative cases. The validation docs are unusually careful about what was *not* proven.

That said, I found one probable behavioral regression baked into a rewritten test, several contract weaknesses that the current test suite cannot catch, duplicated build logic carrying a latent bug, and a set of documentation drift issues. The biggest structural risk is not in the validated macOS Debug core profile but in the *unvalidated* seams: manifest semantics (types dropped, error poisoning), pyopenms configuration identity, and consumer re-discovery of already-pinned dependencies.

## 2. Findings

### AR-01 — Tool "types" silently dropped by the manifest schema; extracted CLI test bakes in the loss
- **Priority:** P1 · **Confidence:** high (≈90%; one baseline-comparison step would make it conclusive)
- **Locations:**
  - `packages/cli/source/APPLICATIONS/ToolHandler.cpp:135-160` — manifest rows become `Internal::ToolDescription(name, entry.category)`; `types` is never populated.
  - `packages/cli/source/APPLICATIONS/TOPPBase.cpp:2547-2554` — `-write_ctd`/CWL/JSON iterate `ToolHandler::getTypes(tool_name_)`; empty list ⇒ exactly one CTD per tool.
  - `packages/desktop/gui/source/VISUAL/APPLICATIONS/TOPPASBase.cpp:358-363` — TOPPAS builds per-type sub-entries from `getTypes`; now always empty for product tools.
  - `packages/cli/tests/source/ToolHandler_test.cpp:51-56` — now asserts `ToolHandler::getTypes("IsobaricAnalyzer").empty() == true`.
  - `packages/topp/src/IsobaricAnalyzer.cpp:161-208` — the tool registers a `type` option with per-method subsections; its defaults vary by type.
  - Manifest schema has exactly four columns (name, category, version, executable): `packages/cli/README.md:14`, `packages/topp/tools.json` (no `types` field anywhere in the 131 entries).
- **Trigger and consequence:** In the baseline, `ToolHandler` was a compiled-in catalogue whose `ToolDescription` carried `types` for typed tools (IsobaricAnalyzer is the canonical example: quant methods itraq*/tmt*). The TSV manifest cannot express types, so for all 151 product tools `getTypes` returns `{}`. Observable consequences: `-write_ctd` writes one CTD instead of one per type (upstream file naming is `<tool><type>.ctd` per TOPPBase.cpp:2554), KNIME/Galaxy CTD generation loses per-type variants, and the TOPPAS tool tree loses sub-entries. Internal `.ttd` tools still support types via `ToolDescriptionHandler` (core `ToolDescription.h:75-123`), so the API is now half-fed.
- **Evidence / falsification:** Diff baseline `src/openms/source/APPLICATIONS/ToolHandler.cpp` at `ca3229603` for `ToolDescription` entries with non-empty types; the upstream `ToolHandler_test.cpp` asserted a non-empty type list for IsobaricAnalyzer — the extracted test asserting `.empty()` for the same tool (with the IDMapper assertion unchanged) strongly suggests the test was edited to match new behavior rather than the behavior being intentional. Runtime check: `IsobaricAnalyzer -write_ctd out/` on 3.6 vs the 4.0 build and compare file sets.
- **Classification:** introduced regression (behavioral), compounded by a test-quality issue (assertion updated to match the regression).
- **Fix / acceptance:** Extend the manifest schema (versioned) with an optional fifth field for a comma-separated type list, populate it in `tools.json` for the affected tools, and restore per-type CTD output. Acceptance: a CLI test asserting the exact upstream type list for IsobaricAnalyzer; a TOPP-level test comparing `-write_ctd` output file count against a recorded baseline; a schema-version negotiation note in the manifest header (the plan already flags manifest versioning as missing).

### AR-02 — One malformed or duplicated manifest anywhere breaks every tool and can crash the GUI
- **Priority:** P1 · **Confidence:** high (statically traceable)
- **Locations:**
  - `packages/cli/source/APPLICATIONS/ToolHandler.cpp:111-126` — any malformed line or duplicate tool name in *any* discovered prefix throws `Exception::InvalidValue`.
  - `packages/cli/source/APPLICATIONS/TOPPBase.cpp:129` — the TOPPBase constructor calls `ToolHandler::getToolVersion(tool_name_)` unconditionally; a poisoned registry aborts *every* TOPP tool at startup, including unrelated ones, and including `-help`.
  - GUI call sites without `try/catch`: `packages/desktop/gui/source/VISUAL/MISC/GUIHelpers.cpp:71` (`startTOPPView`), `packages/desktop/gui/source/VISUAL/TOPPASToolVertex.cpp:106,663`, `packages/desktop/gui/source/VISUAL/DIALOGS/TOPPASToolConfigDialog.cpp:173`. An `InvalidValue`/`FileNotFound` escaping these Qt slots terminates the application.
  - `packages/cli/source/APPLICATIONS/ToolHandler.cpp:125` — duplicate names across *different* product prefixes throw; there is no precedence/shadowing policy (the plan itself admits "conflicting installed product policies … need acceptance coverage").
- **Trigger:** a truncated or hand-edited `*.tools.tsv` under any prefix in `OPENMS_TOOL_PREFIX_PATH`, or two products installing the same tool name (e.g., a staging prefix combining separately built products — exactly the layout `test-data` promotes).
- **Evidence / falsification:** CLI `tests/source/ToolManifest_test.cpp:84-102` proves the throw-on-malformed behavior is intended for a single manifest; no test covers "tool A works while unrelated manifest B is corrupt" or "two prefixes export the same tool". Repro: create two prefixes each declaring `FileInfo`, then run any tool.
- **Classification:** deliberate transitional boundary (strictness is intentional) with an unvalidated availability risk and missing precedence policy; the uncaught-throw path in the GUI is an introduced hazard relative to upstream's compiled catalogue (which could not be malformed at runtime).
- **Fix / acceptance:** Catch per-manifest parse errors, log the offending file, and exclude only that manifest; define first-prefix-wins or explicit error for cross-prefix duplicates (and document it); wrap GUI resolver calls in a handler that surfaces a dialog instead of terminating. Acceptance tests: mixed valid/corrupt prefix set; duplicate-name two-prefix case; GUI unit test (Qt TestLib) exercising `startTOPPView` with a broken registry.

### AR-03 — Manifest generation duplicated across three repositories, carrying a stale-variable bug and no drift guard
- **Priority:** P1 · **Confidence:** high
- **Locations:** `packages/topp/CMakeLists.txt:16-31`, `packages/flash/CMakeLists.txt:10-25`, `packages/openswath/CMakeLists.txt:16-32` — near-identical blocks.
- **Bug:** the inner lookup loop sets `category` only when a `tools.json` entry matches (`if(name STREQUAL tool) string(JSON category …)`); `category` is **never reset per outer iteration**. A tool present in `executables.cmake` (`package_tools`) but missing from `tools.json` silently inherits the *previous* tool's category in the installed manifest. Additionally, the JSON is re-parsed per tool with an O(tools²) `string(JSON …)` scan (~131 × 131 queries at configure time in TOPP).
- **Missing guard:** `tests/test_split.py:21-30` cross-checks `tools.json` against the baseline inventory and `src/<name>.cpp` existence, but nothing compares `executables.cmake` (`package_tools`) against `tools.json` — so the drift that triggers the stale-category bug is undetectable today.
- **Classification:** introduced defect (latent; no current mismatch observed — I spot-counted 131/19/1 entries and they match the documented partition) + code duplication + configure-time inefficiency.
- **Fix / acceptance:** Extract a single `openms4_tool_manifest()` function (ship it from the CLI package's installed CMake modules, which all three products already require), parse `tools.json` once into a name→category map, `FATAL_ERROR` on a tool missing metadata, and reset variables per iteration. Acceptance: a source test asserting `executables.cmake` ≡ `tools.json` name sets for all three packages; a configure test with a deliberately missing entry proving hard failure.

Acceptance: a contract test asserting every `OPENMS_*` macro defined on the core target is referenced in sources; the mock-SDK contract test updated for the renamed variable.

### AR-05 — Source-revision identity cannot distinguish a dirty working tree
- **Priority:** P2 · **Confidence:** high
- **Locations:** `packages/core/CMakeLists.txt:251-264` (`rev-parse HEAD`, no dirtiness check); same pattern in every consumer via `openms4_source_revision` (`packages/cli/cmake/OpenMS4Dependencies.cmake:46-71` and six identical copies). The validation report itself had to special-case this: `docs/core-native-validation.md:87` admits the development build "initially embedded the preceding commit … that alone does not identify the uncommitted changes under test".
- **Consequence:** two SDK builds from the same SHA but different content produce identical identity; the whole "exact source pins ⇒ reject wrong revision" machinery (including `test_wrong_core_pin_is_rejected` in `tests/test_consumer_configure.py:47-50`) cannot catch the most common real-world case: local modifications.
- **Classification:** unvalidated risk / identity gap (inherited pattern from upstream git-tracking, but the experiment elevated the SHA to a security-relevant pin).
- **Fix / acceptance:** Append `-dirty` (or fail acceptance builds) when `git status --porcelain` is non-empty; record the flag in `OpenMSConfig`/`OpenMSData` metadata and the manifest. Acceptance: configure test that mutates a tracked file and proves the embedded revision changes; the acceptance runner rejecting a dirty build when `--expected-revision` is a clean 40-hex SHA.

### AR-08 — Consumers re-discover Boost and Eigen with looser constraints than the SDK's exact pins
- **Priority:** P2 · **Confidence:** high
- **Locations:** `packages/topp/CMakeLists.txt:14-15` (`find_package(Boost 1.81 REQUIRED COMPONENTS regex)`, `find_package(Eigen3 3.4 REQUIRED CONFIG)`); SDK contract is `find_dependency(Boost <exact> EXACT …)` and `Eigen3 3.4.0...<6` (`packages/core/cmake/OpenMSConfig.cmake.in:10-14`).
- **Trigger:** a consumer host where `CMAKE_PREFIX_PATH` resolves Boost/Eigen to a *different* installation than the SDK's. `OpenMSConfig` creates imported targets for its Boost; TOPP's subsequent looser `find_package(Boost 1.81)` can find a different Boost (module vs config mode, different prefix order) and re-point or conflict with the already-defined targets. Then a TOPP executable links Boost.regex A while libOpenMS was built against Boost.regex B — a classic ODR/ABI hazard. Eigen has the symmetric problem (no upper bound here, `<6` in the SDK).
- **Classification:** unvalidated risk (no native consumer build exists yet) / consistency defect in the build contract.
- **Fix / acceptance:** Consumers should use the targets the SDK already imported (guard with `if(NOT TARGET Boost::regex)` before finding, and pin the same version when finding is unavoidable). Acceptance: mock-SDK configure test where the ambient Boost version differs from the SDK-pinned one; must fail.

### AR-12 — Library calls `exit(1)` on bad data override: hostile to embedders (pyopenms)
- **Priority:** P2 · **Confidence:** high (static); runtime UX unvalidated
- **Locations:** `packages/core/src/openms/source/SYSTEM/File.cpp:775-791` — an invalid `OPENMS_DATA_PATH` prints to `std::cerr` and calls `exit(1)` inside `File::resolveOpenMSDataPath_()`. This runs on first data access, which for Python is at `import pyopenms`/first use inside the *interpreter* process.
- **Consequence:** a user (or a Jupyter kernel, or FLASHApp's streamlit process) with a stale `OPENMS_DATA_PATH` gets an immediate process kill with no catchable exception. The acceptance tests (`ExpectInvalidDataOverride.cmake`) lock in the exit-1 behavior, so this is deliberate for CLI tools; nobody has tested or specified the embedding experience.
- **Classification:** deliberate transitional boundary with an unvalidated embedding risk (behavior largely inherited from upstream, but the stricter "invalid override fails" semantics are new).
- **Fix / acceptance:** Introduce a throw-on-invalid-override path (e.g., `Exception::FailedAPICall`) that CLI `TOPPBase` converts to exit(1), letting embedded consumers catch it. Acceptance: a Python test asserting a catchable exception on a bad override instead of interpreter death; keep the existing exit-code test for the CLI path.

Acceptance: unit tests for `run_python` missing-script path and for double-start/stop races; a container lint asserting no `.git` in the image context.

### AR-18 — Concurrency/global-state notes (inherited, low)

- **Locations:** `packages/core/src/openms/source/CONCEPT/VersionInfo.cpp:112-147` — hand-rolled `static bool is_initialized` + separate `static std::string result` pairs are not thread-safe on first concurrent call (the codebase elsewhere uses the correct immediately-invoked-lambda idiom, e.g. `File.cpp:698,706`). `packages/cli/source/APPLICATIONS/ToolHandler.cpp:198-204,259-260` — lazy static `tools_internal_`/`tools_internal_loaded_` without synchronization; also `packageTools()` re-scans and re-parses every manifest on *each* `getTOPPToolList`/`getToolVersion`/`findExecutable` call (TOPPBase startup alone triggers two full scans: ctor line 129 and `main` line 159), while the sibling internal-tools list is cached — inconsistent and, for GUI sessions that resolve tools repeatedly, needlessly I/O-heavy.
- **Classification:** inherited upstream defects (VersionInfo, ToolHandler statics) + introduced inefficiency (manifest rescan).
- **Fix / acceptance:** Meyers-singleton or `std::call_once` for both; cache the parsed manifest map behind a thread-safe invalidation-aware accessor. Acceptance: a TSAN run (not performed here) plus a micro-benchmark assertion in a performance test.
